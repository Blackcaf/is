# Vehicle Information System

Информационная система для управления объектами класса `Vehicle` (транспортные средства).
Реализована как Spring Boot приложение с разделением на слои, ORM EclipseLink и базой данных PostgreSQL.
Сборка — Maven, пакет — WAR, сервер приложений — WildFly 23 (Java 17).
Приложение также запускается локально на встроенном Tomcat.

## Предметная область

### Vehicle

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | `Long` | генерируется БД, уникальное, `> 0` |
| `name` | `String` | не `null`, не пустая строка |
| `coordinates` | `Coordinates` | не `null`, связь многие-к-одному |
| `creationDate` | `ZonedDateTime` | заполняется автоматически, не `null`, не изменяется |
| `type` | `VehicleType` | может быть `null` |
| `enginePower` | `double` | `> 0` |
| `numberOfWheels` | `Long` | может быть `null`, иначе `> 0` |
| `capacity` | `Long` | не `null`, `> 0` |
| `distanceTravelled` | `float` | `> 0` |
| `fuelConsumption` | `double` | `> 0` |
| `fuelType` | `FuelType` | может быть `null` |

`VehicleType`: `DRONE`, `BOAT`, `SHIP`, `BICYCLE`.

`FuelType`: `GASOLINE`, `KEROSENE`, `ELECTRICITY`, `NUCLEAR`, `ANTIMATTER`.

Порядок объявления значений `FuelType` используется в специальной операции сравнения:
`GASOLINE < KEROSENE < ELECTRICITY < NUCLEAR < ANTIMATTER`.

### Coordinates

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | `Long` | генерируется БД, уникальное, `> 0` |
| `x` | `Double` | не `null`, `<= 862` |
| `y` | `int` | `> -860` |

Один объект `Coordinates` может быть связан с несколькими `Vehicle`.
При удалении `Coordinates` связанные транспортные средства переназначаются на другой объект.

### Новые ограничения уникальности (ЛР2)

По заданию требовалось самостоятельно сформулировать **2–3 новых ограничения
уникальности предметной области**. Реализованы два ограничения; они согласуются
с преподавателем и проверяются **только программно, в бизнес-логике**.
В БД для них намеренно не создаются `UNIQUE`-индексы и ограничения.

| Ограничение | Правило | Где проверяется |
| --- | --- | --- |
| `U1: Vehicle.name` | название транспортного средства уникально без учёта регистра и пробелов по краям | `VehicleService` при создании/обновлении, `VehicleImportTxService` при импорте |
| `U2: Coordinates(x, y)` | пара координат `(x, y)` уникальна; при создании `Vehicle` с уже существующей парой используется существующий `Coordinates` | `VehicleService.resolveCoordinates`, `CoordinatesService.create`, `VehicleImportTxService` |

Для `U1` при нарушении возвращается `409 Conflict` с ошибкой в поле `name`.
Для `U2` прямой `POST /api/coordinates` с существующей парой возвращает `409`,
а создание/редактирование `Vehicle` переиспользует существующий `Coordinates`.

Так как проверки `U1`/`U2` устроены по схеме «прочитали — проверили — записали»,
транзакции изменения выполняются на уровне изоляции `SERIALIZABLE`
(обоснование — в разделе [Изоляция транзакций](#изоляция-транзакций)).

## Пользователи и роли

В системе есть два типа пользователей:

| Роль | Возможности |
| --- | --- |
| `USER` | создание/редактирование/удаление объектов, импорт, просмотр **только своих** операций импорта |
| `ADMIN` | те же операции + просмотр **всех** операций импорта |

Аутентификация — сессионная (`JSESSIONID`), пароли хранятся в виде BCrypt-хешей.
При первом запуске создаются тестовые пользователи (управляется параметром
`app.users.seed-enabled`, переменная окружения `APP_USERS_SEED_ENABLED`):

| Логин | Пароль | Роль |
| --- | --- | --- |
| `admin` | `admin` | `ADMIN` |
| `admin2` | `admin2` | `ADMIN` (второй администратор для JMeter) |
| `user` | `user` | `USER` |
| `user2` | `user2` | `USER` |

Для промышленной эксплуатации сидирование тестовых пользователей нужно отключить.
Неавторизованные запросы к `/api/**` получают `401`.

## Сборка и тесты

Требуется JDK 17 и Maven 3.8+.

```bash
mvn clean package
```

Результат сборки: `target/vehicle-is.war` (исполняемый WAR, собранный Spring Boot Maven Plugin).

Только тесты:

```bash
mvn test
```

Тесты покрывают валидацию, создание/обновление/удаление, специальные операции,
добавление колёс и ограничения `Coordinates`, новые ограничения уникальности,
оптимистическую блокировку, разбор CSV, атомарность импорта, запись неудачного
импорта в историю, фильтрацию истории по ролям и правило отображения
`addedCount`.

## База данных

Параметры подключения задаются в `src/main/resources/application.properties`:

```
app.database.url=jdbc:postgresql://pg:5432/studs
app.database.user=${DB_USER:${user.name}}
app.database.password=${DB_PASSWORD:}
app.database.ddl-generation=create-or-extend-tables
```

`AppConfig` читает эти значения и передаёт их EclipseLink, переопределяя JDBC-параметры
из `persistence.xml`. Если `DB_USER` не задан, используется имя текущего пользователя ОС,
`DB_PASSWORD` по умолчанию пустой.

Схема создаётся скриптом `src/main/resources/schema-postgres.sql`:

```bash
psql -h pg -U "$DB_USER" -d studs -f src/main/resources/schema-postgres.sql
```

Скрипт создаёт таблицы `coordinates`, `vehicle`, `app_user`, `import_operation`,
индексы, CHECK-ограничения и колонку `vehicle.version` для оптимистической
блокировки. Скрипт идемпотентен (`CREATE TABLE IF NOT EXISTS`,
`CREATE INDEX IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`).

Важно: новые ограничения уникальности `U1` (`Vehicle.name`) и `U2`
(`Coordinates(x, y)`) в БД **не создаются**. В схеме нет `UNIQUE`-индексов
по этим полям — они проверяются только в бизнес-логике приложения, как требует
задание ЛР2. `UNIQUE` есть только у `app_user.username`, что относится к учётным
записям, а не к предметной области.

В `persistence.xml` задано `eclipselink.ddl-generation.output-mode=none`, поэтому
приложение не создаёт и не изменяет схему автоматически, несмотря на значение
`app.database.ddl-generation`. Перед первым запуском примените `schema-postgres.sql`.

## Веб-интерфейс

Одностраничное приложение на hash-маршрутах:

- `#/` — список транспортных средств;
- `#/view/:id` — подробная информация об объекте;
- `#/new` — открывает диалог создания объекта;
- `#/import` — загрузка CSV-файла и массовый импорт;
- `#/history` — история операций импорта;
- `#/special` — специальные операции.

Возможности:

- вход в систему по логину и паролю, отображение текущего пользователя и роли;
- постраничный вывод (5, 8, 10, 20 или 50 строк);
- сортировка по клику на заголовок любой колонки (повторный клик меняет направление);
- фильтрация по выбранной колонке с частичным совпадением подстроки;
- создание и редактирование в модальном диалоге;
- клиентская и серверная валидация с подсветкой конкретных полей;
- выбор существующего `Coordinates` или создание нового вместе с `Vehicle`;
- просмотр связанного объекта `Coordinates` на странице деталей;
- удаление с подтверждением (с передачей версии для защиты от конкурентного удаления);
- автоматическое обновление списка и страницы деталей при изменениях,
  сделанных другим клиентом (Server-Sent Events);
- индикатор состояния SSE-соединения в шапке;
- удаление `Coordinates` с переназначением связанных `Vehicle`;
- загрузка CSV-файла через браузер и отображение результата импорта;
- таблица истории импорта: id операции, статус, пользователь, число добавленных
  объектов (только для успешных операций), файл, время, текст ошибки.
  Обычный пользователь видит только свои операции, администратор — все.

Базовый адрес API вычисляется в `app.js` из пути загруженного скрипта, поэтому
интерфейс работает и в корне домена, и с контекстным путём `/vehicle-is`.

## Импорт объектов

### Формат файла

Формат согласован с преподавателем: **CSV, UTF-8**, первая строка — заголовок.
Разделитель — `;` или `,` (определяется автоматически по заголовку).
Поддерживаются кавычки и экранирование кавычек удвоением (`""`).

Вложенный объект `Coordinates` задаётся **в той же строке**, что и основной
`Vehicle`, колонками `coordinates.x` и `coordinates.y`. Идентификатор
`Coordinates` в файле не задаётся: если пара `(x, y)` уже есть, она
переиспользуется; иначе создаётся новый `Coordinates` в той же транзакции.

| Колонка | Обязательна | Ограничение |
| --- | --- | --- |
| `name` | да | не пустая, уникальна без учёта регистра (`U1`) |
| `coordinates.x` | да | число `<= 862` |
| `coordinates.y` | да | целое `> -860` |
| `type` | нет | `DRONE`, `BOAT`, `SHIP`, `BICYCLE` |
| `enginePower` | да | число `> 0` |
| `numberOfWheels` | нет | целое `> 0` |
| `capacity` | да | целое `> 0` |
| `distanceTravelled` | да | число `> 0` |
| `fuelConsumption` | да | число `> 0` |
| `fuelType` | нет | `GASOLINE`, `KEROSENE`, `ELECTRICITY`, `NUCLEAR`, `ANTIMATTER` |

Пример (`src/main/resources/static/import-sample.csv`):

```csv
name;coordinates.x;coordinates.y;type;enginePower;numberOfWheels;capacity;distanceTravelled;fuelConsumption;fuelType
Импорт-Квадрокоптер;12.5;7;DRONE;15.5;4;2;120.0;3.5;ELECTRICITY
Импорт-Катер;40.0;12;BOAT;220;;8;5400.5;18.2;GASOLINE
Импорт-Велосипед;86.25;-15;BICYCLE;0.5;2;1;350.0;0.1;
```

Пустые необязательные значения означают `null`. Пустые строки пропускаются.
Максимальный размер файла — 5 МБ.

### Транзакционность и валидация

Импорт выполняется в **одной транзакции** уровня `SERIALIZABLE`:

1. файл полностью разбирается и все строки валидируются;
2. проверяются ограничения предметной области и уникальность `U1`/`U2`;
3. проверяются дубликаты названий внутри самого файла;
4. только после успешной проверки всех строк объекты сохраняются и выполняется `flush`;
5. любая ошибка (валидация, уникальность, ошибка БД) приводит к откату —
   **ни один объект не создаётся**.

Ошибки возвращаются с привязкой к строке и полю, например:

```json
{
  "operationId": 42,
  "status": "FAILED",
  "totalRows": 3,
  "errors": {
    "row 3.enginePower": "Значение поля enginePower должно быть больше 0",
    "general": "Импорт не выполнен: ни один объект не был добавлен"
  }
}
```

Запись об операции создаётся в **отдельной транзакции** до начала импорта,
поэтому при откате она сохраняется в истории со статусом `FAILED`. Для успешной
операции статус `SUCCESS` и число добавленных объектов фиксируются в той же
транзакции, что и сами объекты.

### API импорта

| Метод | Путь | Описание |
| --- | --- | --- |
| `POST` | `/imports` | загрузить CSV (`multipart/form-data`, поле `file`), ответ `201` |
| `GET` | `/imports?page=1&size=20` | история импорта (своя для `USER`, все для `ADMIN`) |

Ответ успешного импорта:

```json
{
  "operationId": 42,
  "status": "SUCCESS",
  "addedCount": 3,
  "totalRows": 3
}
```

## История импорта

Хранится в таблице `import_operation`. В интерфейсе `#/history` отображаются:

- `id` операции;
- статус (`RUNNING`, `SUCCESS`, `FAILED`);
- пользователь, запустивший операцию;
- число добавленных объектов — **только для `SUCCESS`** (для остальных `null`);
- имя файла, время начала/завершения и текст ошибки (дополнительно).

`GET /api/imports` для обычного пользователя автоматически фильтрует операции
по `user_id` текущего пользователя; администратор получает все операции.
Фильтрация выполняется на сервере, а не только в интерфейсе.

## Изоляция транзакций

Исходная система ЛР1 использовала уровень по умолчанию (`READ_COMMITTED`
в PostgreSQL). Для ЛР2 выбраны следующие уровни:

| Операция | Уровень | Почему |
| --- | --- | --- |
| чтение списка, карточки, специальные операции | `READ_COMMITTED` | достаточно для чтения; не блокирует другие транзакции |
| создание/обновление/удаление `Vehicle` | `SERIALIZABLE` | проверки `U1`/`U2` выполняются в приложении по схеме «прочитали — проверили — записали»; при `READ_COMMITTED` возможна аномалия *write skew*: два пользователя одновременно не находят дубликат и оба вставляют его |
| импорт | `SERIALIZABLE` | та же причина + импорт должен быть атомарным и не конфликтовать с параллельным созданием/импортом |
| создание `Coordinates` | `SERIALIZABLE` | проверка уникальности пары `(x, y)` |
| добавление колёс, удаление `Coordinates` с переназначением | `SERIALIZABLE` | конкурентные изменения связанных объектов |
| запись истории импорта (`start`, `markFailed`) | `READ_COMMITTED`, `REQUIRES_NEW` | отдельная короткая транзакция, не должна откатываться вместе с импортом |

Дополнительно для обнаружения одновременного редактирования/удаления одного
объекта добавлено поле `Vehicle.version` (`@Version`) и оптимистическая
блокировка. Клиент передаёт `version` в `PUT` и `DELETE`; при несовпадении
возвращается `409 Conflict`. Это позволяет отличить «гонку» от обычного
последнего изменения и не потерять данные.

Spring передаёт уровень изоляции в EclipseLink (`EclipseLinkJpaDialect`
устанавливает `DatabaseLogin.transactionIsolation`), поэтому аннотации
`@Transactional(isolation = ...)` реально применяются к соединению PostgreSQL.
Если PostgreSQL прерывает транзакцию из-за конфликта сериализации (SQLState
`40001`), Spring транслирует это в `ConcurrencyFailureException`, а приложение
возвращает `409` — частичных изменений не остаётся.

## Нагрузочное тестирование Apache JMeter

Сценарий: `jmeter/vehicle-is-load-test.jmx`. Он имитирует одновременную работу
двух администраторов и пользователя и проверяет:

1. **создание** — два администратора одновременно создают объект с одинаковым
   уникальным названием; ожидается ровно один `201` и один `409`;
2. **редактирование** — два администратора одновременно обновляют один объект
   с одной и той же версией; ожидается один `200` и один `409`;
3. **удаление** — один администратор обновляет объект, второй одновременно
   удаляет его; успешно завершается ровно одна операция, вторая получает
   `404` или `409`, ответов `500` быть не должно;
4. **импорт** — корректный CSV из 3 строк (с вложенными координатами) и
   некорректный CSV; после некорректного импорта проверяется, что не создан
   ни один объект (атомарность);
5. **история** — обычный пользователь видит свою операцию, администратор
   видит операции пользователя.

Запуск (из корня проекта, приложение уже запущено):

```bash
jmeter -n -t jmeter/vehicle-is-load-test.jmx \
  -l jmeter/results.jtl -e -o jmeter/report
```

Параметры можно переопределить:

```bash
jmeter -n -t jmeter/vehicle-is-load-test.jmx \
  -Jhost=localhost -Jport=8180 -Jcontext=/vehicle-is \
  -l jmeter/results.jtl -e -o jmeter/report
```

По умолчанию: `host=localhost`, `port=8080`, `context=` (локальный Spring Boot).
Для WildFly: `-Jport=8180 -Jcontext=/vehicle-is`. Файл `admins.csv` содержит
`admin/admin` и `admin2/admin2`; для сценария нужны все четыре тестовых
пользователя, создаваемые при первом запуске.

Итоги проверяются в `PostThreadGroup` по агрегированным счётчикам: сценарий
падает, если нарушено ожидаемое распределение кодов ответа, импортировано не
3 объекта, после ошибочного импорта найдены объекты или история импорта
отфильтрована неверно.

### Ожидаемые результаты

Сценарий спроектирован так, чтобы подтвердить следующее поведение:

При конкурентном создании объекта с одинаковым названием без `SERIALIZABLE`
оба запроса проходят проверку `U1` и создают дубликат. После перевода
изменяющих транзакций на `SERIALIZABLE` PostgreSQL прерывает одну из
конфликтующих транзакций (`40001`), приложение возвращает `409`, дубликат
не создаётся. Для конкурентного редактирования/удаления дополнительно введена
оптимистическая блокировка по `version`: второй клиент получает `409` вместо
молчаливой перезаписи или удаления чужого изменения. Импорт остаётся
атомарным: ошибка в любой строке откатывает всю транзакцию, а запись истории
сохраняется отдельно со статусом `FAILED`.

> В среде разработки, где готовилась работа, PostgreSQL был недоступен,
> поэтому сценарий JMeter ещё не прогонялся. Перед защитой его нужно выполнить
> по инструкции выше и приложить отчёт `jmeter/report`. Если фактические коды
> ответов отличатся от ожидаемых, корректируются обработчики конфликтов, а не
> assertions сценария.

## REST API

Базовый префикс: `/api` (при развёртывании WAR — `/vehicle-is/api`).

### Аутентификация

| Метод | Путь | Описание |
| --- | --- | --- |
| `POST` | `/auth/login` | вход, тело `{"username":"...","password":"..."}`, устанавливает сессию |
| `POST` | `/auth/logout` | выход, ответ `204` |
| `GET` | `/auth/me` | текущий пользователь `{"id":1,"username":"admin","role":"ADMIN"}` |

Все остальные `/api/**` требуют активной сессии; иначе ответ `401`.
Сессия хранится в `JSESSIONID`, поэтому JMeter и браузер работают одинаково.

### Транспортные средства

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/vehicles` | постраничный список |
| `POST` | `/vehicles` | создать объект, ответ `201` |
| `GET` | `/vehicles/{id}` | получить объект |
| `PUT` | `/vehicles/{id}` | обновить объект |
| `DELETE` | `/vehicles/{id}?version=N` | удалить объект (необязательная проверка версии), ответ `{"deleted": id}` |
| `GET` | `/vehicles/events` | поток SSE-событий |

Параметры списка:

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `filterField` | — | колонка фильтра |
| `filterValue` | — | подстрока для частичного совпадения |
| `sortField` | `id` | колонка сортировки |
| `asc` | `true` | направление сортировки |
| `page` | `1` | номер страницы, начиная с 1 |
| `size` | `10` | размер страницы, от 1 до 100 |

Доступные поля фильтрации и сортировки:
`id`, `name`, `type`, `fuelType`, `creationDate`, `enginePower`, `numberOfWheels`,
`capacity`, `distanceTravelled`, `fuelConsumption`, `coordX`, `coordY`.

Фильтрация по строковым полям (`name`, `type`, `fuelType`) выполняется без учёта регистра.
Для остальных полей значение приводится к строке и сравнивается как подстрока.

Пример ответа списка:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "size": 10
}
```

Тело создания и обновления (`VehicleDto`):

```json
{
  "name": "Quadrocopter",
  "coordinates": { "id": null, "x": 12.5, "y": 7 },
  "type": "DRONE",
  "enginePower": 15.5,
  "numberOfWheels": 4,
  "capacity": 2,
  "distanceTravelled": 120.0,
  "fuelConsumption": 3.5,
  "fuelType": "ELECTRICITY",
  "version": 0
}
```

Если у `coordinates` задан `id`, используется существующий объект `Coordinates`.
Если `id` равен `null`, сначала ищется существующая пара `(x, y)` (ограничение `U2`);
если она есть — переиспользуется, иначе создаётся новый объект.

Поле `version` возвращается в ответах и используется для оптимистической
блокировки. При `PUT` клиент передаёт полученную ранее версию; если объект уже
изменён, возвращается `409`. При `DELETE` версия передаётся необязательным
параметром `version`.

Валидация выполняется в сервисном слое. Ошибки возвращаются с кодом `400`:

```json
{
  "errors": {
    "coordinates.x": "Максимальное значение поля x: 862"
  }
}
```

Ошибки, не привязанные к конкретному полю, и ответы `404` имеют ключ `general`:

```json
{
  "errors": {
    "general": "Транспортное средство с id=42 не найдено"
  }
}
```

Нарушение новых ограничений уникальности и конфликт версий возвращают `409`:

```json
{
  "errors": {
    "name": "Транспортное средство с названием «Quadrocopter» уже существует"
  }
}
```

```json
{
  "errors": {
    "general": "Объект уже изменён другим пользователем. Обновите данные и повторите редактирование."
  }
}
```

### Coordinates

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/coordinates` | список всех объектов |
| `POST` | `/coordinates` | создать объект, ответ `201` |
| `DELETE` | `/coordinates/{id}?replacementId=N` | переназначить связанные `Vehicle` и удалить объект |

Параметр `replacementId` обязателен и должен указывать на другой объект `Coordinates`.

### SSE

`GET /vehicles/events` возвращает поток `text/event-stream`.
Имена событий: `created`, `updated`, `deleted`.
Данные события содержат полный `VehicleDto`:

```json
{
  "vehicle": {
    "id": 1,
    "name": "Quadrocopter",
    "coordinates": { "id": 3, "x": 12.5, "y": 7 },
    "creationDate": "2026-10-27 12:00:00 MSK",
    "type": "DRONE",
    "enginePower": 15.5,
    "numberOfWheels": 4,
    "capacity": 2,
    "distanceTravelled": 120.0,
    "fuelConsumption": 3.5,
    "fuelType": "ELECTRICITY",
    "version": 0
  }
}
```

События публикуются только после успешного коммита транзакции, поэтому клиент
получает уже сохранённый идентификатор объекта. Механизм работает в пределах
одного экземпляра WildFly.

## Специальные операции

| Метод | Путь | Описание | Ответ |
| --- | --- | --- | --- |
| `GET` | `/special/fuel-consumption-sum` | сумма `fuelConsumption` всех объектов | `{"result": 12.5}` |
| `GET` | `/special/min-by-type` | объект с минимальным `type` (по порядку enum) | `VehicleDto` или `404` |
| `GET` | `/special/count-fuel-type-greater?fuelType=X` | количество объектов, у которых `fuelType` больше `X` | `{"result": 3}` |
| `GET` | `/special/by-type?type=X` | все объекты заданного `VehicleType` | `{"items": [...]}` |
| `POST` | `/special/{id}/wheels?count=N` | добавить `N` колёс объекту с `id` | обновлённый `VehicleDto` |

Для `min-by-type` объекты с `type = null` не учитываются.
Для `count-fuel-type-greater` объекты с `fuelType = null` не учитываются,
а сравнение идёт по порядку объявления значений `FuelType`.

Некорректное значение `type` или `fuelType` приводит к ответу `400` с ошибкой
в формате `{"errors": {"type": "..."}}` или `{"errors": {"fuelType": "..."}}`.
Для `wheels` значение `count` должно быть больше `0`.

## Соответствие требованиям ЛР2

| Требование | Реализация |
| --- | --- |
| Импорт через веб-интерфейс, формат согласован с преподавателем | страница `#/import`, `POST /api/imports`; CSV UTF-8 с заголовком, разделитель `;` или `,` (см. [Импорт объектов](#импорт-объектов)) |
| Импорт атомарен: при любой ошибке не создаётся ни один объект | `VehicleImportTxService.importRows` — одна транзакция `SERIALIZABLE`, сохранение только после валидации всех строк; тест `VehicleImportTxServiceTest` |
| Проверка вложенного `Coordinates` в той же строке CSV | колонки `coordinates.x`/`coordinates.y`, ограничения `x <= 862`, `y > -860`; тесты `CsvVehicleParserTest`, `VehicleImportTxServiceTest` |
| История импорта: id операции, статус, пользователь, число добавленных объектов только у успешных | `ImportOperation`, `ImportHistoryService`, `WebMapper`, страница `#/history` |
| `USER` видит только свои операции, `ADMIN` — все | фильтрация по `userId` в `ImportHistoryService.page`, проверяется в JMeter |
| 2–3 новых ограничения уникальности, только в бизнес-логике | `U1` (уникальное имя) и `U2` (уникальная пара координат); в `schema-postgres.sql` по этим полям нет `UNIQUE` |
| JMeter: создание/редактирование/удаление/импорт, конкурентные update/delete и duplicate create, проверка изоляции | `jmeter/vehicle-is-load-test.jmx` |
| Обоснованная смена уровня изоляции | `SERIALIZABLE` для изменений, `READ_COMMITTED` для чтений, `REQUIRES_NEW` для истории; см. [Изоляция транзакций](#изоляция-транзакций) |
| Конструкторная инъекция, без `@Autowired` на полях | все Spring-бины и репозитории принимают зависимости через конструктор; репозитории получают `EntityManagerFactory` и создают shared-`EntityManager` |
| Контроллеры выполняют только свой функционал | в контроллерах нет `try/catch` и бизнес-логики; ошибки — в `ApiExceptionHandler`, SSE — в `VehicleEventStream` |
| Маппинг через `org.mapstruct.Mapper` | единый `WebMapper` для Vehicle, Coordinates, User, ImportResult и ImportOperation |

## Особенности реализации

- Spring Boot управляет конфигурацией и запуском; JPA настроена явно в `AppConfig`.
- Слои разделены: `web` → `service` → `repo` → `domain`.
- Преобразование сущностей в DTO выполняет единый MapStruct-маппер
  `WebMapper` (`componentModel = "spring"`,
  `injectionStrategy = CONSTRUCTOR`). Сервисы не зависят от классов пакета
  `web`.
- Все зависимости внедряются через конструкторы; `@Autowired` на полях не
  используется. Репозитории принимают `EntityManagerFactory` и создают
  shared-`EntityManager` (как у `@PersistenceContext`), поэтому в контексте
  нет двух бинов типа `EntityManager`.
- Контроллеры только принимают запрос, вызывают сервис и маппер и возвращают
  ответ. Обработка исключений централизована, SSE-соединения обслуживает
  `VehicleEventStream`.
- Валидация и бизнес-проверки вынесены в сервисы; Bean Validation дополнена
  проверками в сеттерах доменных классов.
- Ошибки централизованно обрабатываются `ApiExceptionHandler`
  (`@RestControllerAdvice`): `400` для валидации и некорректного JSON,
  `401` для неавторизованных запросов, `404` для отсутствующих объектов,
  `409` для нарушения уникальности и конфликтов версий/сериализации.
- Транзакциями управляет Spring (`@Transactional`, `JpaTransactionManager`);
  изменяющие транзакции используют `SERIALIZABLE`, чтения — `READ_COMMITTED`.
- `creationDate` выставляется в `@PrePersist` и не обновляется при редактировании.
- `Vehicle.version` (`@Version`) обеспечивает оптимистическую блокировку при
  одновременном редактировании/удалении.
- Пароли пользователей хранятся в виде BCrypt-хешей, сессия — `JSESSIONID`.
- Импорт читает CSV в кодировке UTF-8, поддерживает `;` и `,`, кавычки и BOM.
  Вложенные `Coordinates` задаются в той же строке, что и `Vehicle`.
- Идентификатор нового объекта генерируется PostgreSQL (`GENERATED ALWAYS AS IDENTITY`).
- Фильтрация и сортировка строятся по белому списку полей, поэтому имена колонок
  не подставляются в JPQL напрямую из запроса.
- Даты сериализуются как строки; для `creationDate` задан шаблон
  `yyyy-MM-dd HH:mm:ss z`.
- Статические ресурсы отдаются Spring Boot из `classpath:/static`; `index.html`
  используется как welcome-страница.
- `jboss-deployment-structure.xml` отключает JPA-подсистему WildFly,
  чтобы использовался EclipseLink из состава приложения.
